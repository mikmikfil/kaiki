Χωρίς worker δεν φεύγει email και δεν βγαίνει εισιτήριο. Χωρίς cron οι θέσεις εγκαταλελειμμένων πληρωμών μένουν κλειδωμένες. Χωρίς Chromium δεν βγαίνει κανένα PDF. Και τα τρία εδώ, μαζί με τον κωδικό που κρατά το staging μακριά από μηχανές αναζήτησης.

Ο worker της ουράς

Καμία εργασία του Kaiki δεν ορίζει δική της ουρά: όλες πάνε στην default. Emails επιβεβαίωσης, εισιτήρια PDF, παραστατικά, επιστροφές χρημάτων, webhooks της Viva, εξαγωγές, εισαγωγές, ημερολόγια iCal. Δύο διεργασίες αρκούν για staging. 

/etc/supervisor/conf.d/kaiki-staging.conf[program:kaiki-staging-worker]
process_name=%(program_name)s_%(process_num)02d
numprocs=2
directory=/home/kaikistg/kaiki
command=/usr/bin/php8.4 artisan queue:work redis --queue=default --sleep=3 --tries=3 --timeout=120 --max-time=3600
user=kaikistg
environment=HOME="/home/kaikistg",PUPPETEER_SKIP_DOWNLOAD="1"
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
stopwaitsecs=960
redirect_stderr=true
stdout_logfile=/home/kaikistg/kaiki/storage/logs/worker.log
stdout_logfile_maxbytes=10MB
stdout_logfile_backups=3
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl status kaiki-staging-worker:*
--timeout=120 Για τις περισσότερες εργασίες. Όσες ορίζουν δικό τους $timeout (η εισαγωγή: 900) το κρατούν.
stopwaitsecs=960 Σε επανεκκίνηση, ο Supervisor περιμένει να τελειώσει μια εισαγωγή αντί να την κόψει στη μέση.
--max-time=3600 Ο worker ξεκινά από την αρχή κάθε ώρα, ώστε μια διαρροή μνήμης να μην κρατά για πάντα.
HOME Το Chromium γράφει προφίλ και crash reports στο home του χρήστη. Χωρίς HOME μπορεί να μην ξεκινήσει.

Αν ο server δεν έχει Supervisor αλλά η Cretaforce προτιμά systemd, η ίδια εντολή μπαίνει σε ένα kaiki-staging-worker@.service με User=kaikistg, Restart=always και KillSignal=SIGTERM, TimeoutStopSec=960.

Chromium για τα PDF

Η αλυσίδα είναι: PHP (Browsershot) → node → puppeteer από το node_modules της εφαρμογής → το Chromium του KAIKI_CHROME_PATH. Τρέχει με --no-sandbox και χωρίς πρόσβαση στο δίκτυο από το έγγραφο (app/Support/Pdf/ChromiumPdf.php). Ελέγξτε ολόκληρη την αλυσίδα με μία εντολή, ως ο χρήστης του site: 

php8.4 artisan tinker --execute="echo strlen(App\Support\Pdf\ChromiumPdf::render('<h1>Καλημέρα, Αιγαίο</h1>')), PHP_EOL;"

Ένας αριθμός (μερικές δεκάδες χιλιάδες bytes) σημαίνει ότι όλα δουλεύουν. Για να δείτε ότι τα ελληνικά δεν βγαίνουν κουτάκια, γράψτε το PDF σε αρχείο με file_put_contents και ανοίξτε το.

Γιατί όχι το Chromium που κατεβάζει το Puppeteer

Το npm ci θα κατέβαζε ένα Chrome στο ~/.cache/puppeteer, χωρίς τις βιβλιοθήκες συστήματος που χρειάζεται — και αυτές τις εγκαθιστά μόνο ο root. Το CI κάνει το ίδιο που προτείνουμε: PUPPETEER_SKIP_DOWNLOAD=1 και το Chrome του συστήματος. Σε Ubuntu, προτιμήστε το πακέτο google-chrome-stable· το chromium εκεί είναι snap και συχνά δεν τρέχει από υπηρεσία.

Κωδικός και noindex

Το staging είναι δημόσιο και έχει γνωστούς λογαριασμούς. Η εφαρμογή δεν έχει δικό της μηχανισμό για μη-παραγωγικό περιβάλλον: μόνο οι σελίδες κράτησης με token (/b/, /c/, /g/, /q/, /v/) στέλνουν X-Robots-Tag: noindex, ενώ οι σελίδες διοργανωτή είναι σκόπιμα ανοιχτές σε μηχανές αναζήτησης. Άρα στο staging χρειάζονται δύο πράγματα στον web server: κωδικός (Basic Auth) και noindex παντού.

Ο κωδικός μπαίνει παντού εκτός από όσα καλούν άλλοι χωρίς να ξέρουν τον κωδικό:

/api/v1/Το widget από το aegeancr.gr, και το WordPress από τον server του. Το API έχει δικό του κλειδί στο Authorization.
/widget/Το kaiki-widget.js και το manifest.json.
/storage/Φωτογραφίες εκδρομών που δείχνει το WordPress, και τα υπογεγραμμένα λογότυπα.
/webhooks/Η Viva: επιβεβαίωση διεύθυνσης (GET) και ειδοποίηση πληρωμής (POST).
/pay/viva/Επιστροφή του πελάτη από τη Viva (success, failure).
/b/ /c/ /g/ /q/ /v/Οι σελίδες του πελάτη: κράτηση, πληρωμή, στοιχεία επιβατών, προσφορά, κουπόνι. Ανοίγουν από το widget και από τα email.
/sandbox/checkout/Η ψεύτικη πληρωμή του Kaiki, όταν ο διοργανωτής δεν έχει συνδέσει Viva.
/ical/, /upΣυνδρομές ημερολογίου και ο έλεγχος υγείας.

Πίσω από κωδικό μένουν: η αρχική /, τα πάνελ /app και /admin (άρα δύο συνδέσεις — πρώτα ο κωδικός του server, μετά του Kaiki), και ολόκληρες οι σελίδες book.kaiki.testing.gr/…. Όποιος δοκιμάζει σελίδα διοργανωτή δίνει τον κωδικό μία φορά· οι κλήσεις του widget προς /api/v1 στο ίδιο hostname δεν τον χρειάζονται. 

Apache 2.4 — στο VirtualHost (όχι στο public/.htaccess, που είναι στο git)Header always set X-Robots-Tag "noindex, nofollow"

<Location "/">
    AuthType Basic
    AuthName "Kaiki staging"
    AuthUserFile /home/kaikistg/.htpasswd-kaiki
    <RequireAny>
        # THE_REQUEST, όχι REQUEST_URI: μετά το rewrite προς index.php το REQUEST_URI αλλάζει
        Require expr "%{THE_REQUEST} =~ m#^[A-Z]+ /(api/v1|widget|storage|webhooks|pay/viva|b|c|g|q|v|sandbox/checkout|ical)/#"
        Require expr "%{THE_REQUEST} =~ m#^[A-Z]+ /up[ ?]#"
        Require valid-user
    </RequireAny>
</Location>
nginx — στο http{} και στο server{} των δύο subdomains# http {} — $request_uri είναι η αρχική διεύθυνση, και μετά το try_files
map $request_uri $kaiki_auth {
    default  "Kaiki staging";
    "~^/(api/v1|widget|storage|webhooks|pay/viva|b|c|g|q|v|sandbox/checkout|ical)/"  off;
    "~^/up(\?|$)"  off;
}

# server {}
add_header X-Robots-Tag "noindex, nofollow" always;
auth_basic           $kaiki_auth;
auth_basic_user_file /home/kaikistg/.htpasswd-kaiki;
htpasswd -c /home/kaikistg/.htpasswd-kaiki dokimes   # ζητά κωδικό· ή ζητήστε το από την Cretaforce
Δεν δοκιμάστηκε σε server της Cretaforce

Τα δύο snippets είναι γραμμένα για κανονικό Apache 2.4 και nginx· δεν ξέρουμε ποιον από τους δύο (ή και τους δύο, σε σειρά) τρέχει ο πίνακας, ούτε αν επιτρέπει custom οδηγίες στο vhost.
